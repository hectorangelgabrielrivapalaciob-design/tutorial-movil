Control de Versiones

La herramienta que guarda el historial de tu código y te permite trabajar en equipo sin caos

1. ¿Qué es el control de versiones?

Imagina que estás escribiendo un documento importante y cada vez que guardas se crea una copia con fecha y hora. Así puedes volver a cualquier versión anterior si algo sale mal.

El control de versiones (VCS – Version Control System) hace exactamente eso, pero con el código de tu aplicación. Registra quién cambió qué, cuándo y por qué. Permite:

  • Volver a una versión anterior si algo se rompe.
  • Trabajar varias personas al mismo tiempo sin pisarse el trabajo.
  • Ver el historial completo de cambios.
  • Crear “ramas” (versiones paralelas) para probar ideas sin afectar el código principal.

2. ¿Cuáles son los tipos principales?

Existen dos grandes familias:

Centralizados (CVCS)

Hay un solo servidor central. Todos los desarrolladores descargan el código de ahí y suben los cambios al mismo servidor.

Ejemplos: SVN (Subversion), CVS.

Distribuidos (DVCS)

Cada desarrollador tiene una copia completa del historial en su computadora. Puedes trabajar sin internet y luego sincronizar.

Ejemplos: Git, Mercurial.

4. ¿Cómo funciona? (explicación sencilla)

Tomemos Git como ejemplo (es el estándar actual):

  1. Repositorio (repo): la carpeta donde Git guarda todo el historial.
  2. Working directory: los archivos con los que estás trabajando ahora.
  3. Staging area: “zona de preparación”. Aquí eliges qué cambios quieres guardar.
  4. Commit: guardas un “snapshot” (foto) de los cambios con un mensaje explicativo.
  5. Push: subes tus commits al servidor remoto (GitHub, GitLab, etc.).
  6. Pull / Fetch: bajas los cambios que otros hayan subido.

5. Cómo se usa para rastrear y gestionar cambios

Pasos típicos de un día de trabajo con Git:

# 1. Ver el estado de tus archivos
git status

# 2. Agregar archivos al staging
git add archivo.js
# o todos los cambios:
git add .

# 3. Guardar el commit con un mensaje claro
git commit -m "Agrega pantalla de login"

# 4. Subir al servidor
git push origin main

# 5. Crear una rama para una nueva función
git checkout -b feature/notificaciones

# 6. Volver a la rama principal y fusionar
git checkout main
git merge feature/notificaciones

Cada commit queda registrado con autor, fecha y mensaje. Puedes ver el historial con git log y volver a cualquier commit anterior.

6. Ejemplos reales

  • Git + GitHub: la combinación más usada del mundo. Millones de proyectos open source y empresas.
  • Git + GitLab: muy usado en empresas (incluye CI/CD integrado).
  • SVN: todavía se encuentra en muchas empresas tradicionales y proyectos legacy.
  • Bitbucket: repositorios Git y Mercurial (ahora principalmente Git).

1. ¿Qué es la persistencia de datos?

La persistencia es la capacidad de una aplicación de guardar información de forma permanente, de modo que no se pierda cuando cierras la app o apagas el teléfono.

Sin persistencia, cada vez que abrieras la app empezarías de cero (sin preferencias, sin historial, sin datos del usuario).

2. Características principales

  • Durabilidad: los datos sobreviven al cierre de la app y al reinicio del dispositivo.
  • Acceso rápido: especialmente importante en móvil (batería y rendimiento).
  • Seguridad: los datos sensibles deben estar protegidos (cifrado, permisos).
  • Capacidad offline: muchas apps deben funcionar sin internet.
  • Sincronización: poder combinar datos locales con datos en la nube.

3. Formas de persistencia en dispositivos móviles

A) Archivos

Guardar información en archivos de texto, JSON, XML o binarios dentro del almacenamiento del dispositivo.

Ejemplos: preferencias del usuario, caché de imágenes, logs, archivos de configuración.

Ventaja: simple. Desventaja: difícil de consultar y relacionar datos complejos.

B) Bases de datos locales

El rey es SQLite (viene incluido en Android e iOS). También existen Room (Android), Core Data (iOS), Realm, etc.

Permiten guardar datos estructurados (tablas, relaciones) y hacer consultas potentes.

Ideal para: listas de productos, historial, datos de usuario offline.

C) Bases de datos remotas (servicios web)

Los datos viven en un servidor (Firebase, AWS, un backend propio). La app se conecta por internet (API REST, GraphQL…).

Ventaja: los datos están centralizados y accesibles desde cualquier dispositivo. Desventaja: necesita conexión.

4. Tipos de datos según la forma de persistencia

Forma Tipos de datos típicos
Archivos Texto, JSON, imágenes, audio, video, preferencias clave-valor
BD local (SQLite/Room) Datos estructurados: usuarios, productos, mensajes, historial, relaciones
Remoto (API / nube) Cualquier dato que deba compartirse entre dispositivos o usuarios

5. Mecanismos de control de acceso a medios persistentes

  • Bibliotecas de clases: las APIs del sistema (SharedPreferences en Android, UserDefaults en iOS) para datos simples.
  • Clases de SQLite: acceso directo con SQL (más control, más código).
  • Mapeo relacional de objetos (ORM): Room (Android), Core Data, Realm… convierten tablas en objetos de tu lenguaje. Escribes menos SQL y el código es más legible.

6. Proceso de autenticación y consumo de servicios web

Pasos típicos cuando una app móvil habla con un servidor:

  1. Autenticación: el usuario inicia sesión (usuario/contraseña, Google, Apple…). El servidor devuelve un token (JWT u otro).
  2. Guardar el token de forma segura en el dispositivo (Keychain / EncryptedSharedPreferences).
  3. Hacer peticiones: cada vez que la app necesita datos, envía el token en la cabecera de la petición HTTP.
  4. Recibir y procesar: la app recibe JSON (o XML), lo convierte en objetos y lo muestra o guarda localmente.
  5. Refresco de token: cuando el token expira, se pide uno nuevo (refresh token).

Herramientas comunes: Retrofit / OkHttp (Android), URLSession / Alamofire (iOS), Axios o fetch en apps híbridas.

7. Ejemplos prácticos

  • SharedPreferences / UserDefaults: guardar si el usuario ya vio el tutorial de bienvenida.
  • SQLite + Room: app de notas o lista de tareas que funciona sin internet.
  • Firebase Realtime Database / Firestore: chat en tiempo real.
  • API REST propia: app de e-commerce que consulta productos y pedidos en un servidor.

1. ¿Qué son los sensores?

Los sensores son componentes de hardware del dispositivo que miden el mundo físico: movimiento, orientación, luz, ubicación, presión, etc. Las apps pueden leer esos valores y reaccionar (por ejemplo, girar la pantalla, contar pasos o mostrar el mapa).

2. Tipos de sensores en dispositivos móviles

Movimiento
  • Acelerómetro
  • Giroscopio
  • Sensor de gravedad
  • Sensor de rotación
Posición
  • Magnetómetro (brújula)
  • GPS / GNSS
  • Proximidad
Ambientales
  • Luz ambiental
  • Presión (barómetro)
  • Temperatura
  • Humedad
Otros
  • Huella dactilar / Face ID
  • Sensor de frecuencia cardíaca
  • Micrófono y cámara (también se consideran sensores de entrada)

3. Proceso de gestión de sensores (paso a paso)

  1. Declarar permisos
    En Android se declaran en el AndroidManifest.xml. En iOS en el archivo Info.plist. Algunos sensores (ubicación, cámara, micrófono) requieren permiso explícito del usuario.
  2. Habilitar / obtener el sensor
    Se pide al sistema el sensor deseado (por ejemplo Sensor.TYPE_ACCELEROMETER en Android o CMMotionManager en iOS).
  3. Registrar un listener / callback
    La app se “suscribe” para recibir actualizaciones cuando el valor del sensor cambia.
  4. Procesar la información
    Los datos llegan como números (aceleración en m/s², orientación en grados, latitud/longitud…). La app los interpreta y actúa (actualizar UI, guardar, enviar a un servidor, etc.).
  5. Liberar el sensor
    Cuando ya no se necesita, se desregistra el listener para ahorrar batería.
Consejo importante: los sensores consumen batería. Usa la frecuencia de muestreo más baja que te sirva y detén la lectura cuando la app esté en segundo plano si no es necesario.

1. Definición

Los recursos multimedia son todos los elementos de audio, video, imagen y animación que una aplicación utiliza para comunicarse con el usuario o mejorar la experiencia visual y sonora.

2. Tipos de recursos multimedia en programación móvil

  • Imágenes: PNG, JPEG, WebP, SVG (iconos, fondos, fotos).
  • Audio: MP3, AAC, WAV, OGG (efectos de sonido, música, notas de voz).
  • Video: MP4, WebM (tutoriales, trailers, contenido generado por el usuario).
  • Animaciones: Lottie (JSON), GIF, animaciones nativas (Property Animation, Animated en React Native, etc.).
  • Elementos visuales dinámicos: canvas, shaders, partículas, transiciones, mapas, gráficos en tiempo real.

3. Dónde se almacenan en la estructura del proyecto

Plataforma Ubicación típica
Android res/drawable/, res/mipmap/, res/raw/, assets/
iOS Assets.xcassets, carpeta del proyecto, Bundle
Flutter Carpeta assets/ declarada en pubspec.yaml
React Native Carpeta del proyecto o require('./imagen.png')

También se pueden descargar en tiempo de ejecución y guardar en el almacenamiento interno o externo del dispositivo.

4. Componentes de software para usar multimedia

  • Imágenes: ImageView (Android), UIImageView (iOS), componentes de Flutter/React Native.
  • Audio: MediaPlayer / ExoPlayer (Android), AVAudioPlayer (iOS).
  • Video: VideoView / ExoPlayer, AVPlayer.
  • Animaciones: Lottie, MotionLayout, Animated API, Rive.
  • Carga eficiente: Glide, Coil, Picasso (Android); SDWebImage (iOS); cached_network_image (Flutter).

Servicios y Notificaciones

Tareas en segundo plano, notificaciones y servicios en la nube

◆ BACKGROUND · NOTIFICATIONS · CLOUD
FCM / APNs
WorkManager / BG Tasks
Firebase · AWS · Azure

1. Definición

Los servicios permiten que una app realice trabajo aunque el usuario no la esté mirando (descargas, sincronización, reproducción de música). Las notificaciones son mensajes que aparecen en la barra de estado o pantalla de bloqueo para informar al usuario.

2. ¿Qué son las tareas en segundo plano?

Son operaciones que continúan ejecutándose cuando la app está minimizada o la pantalla está apagada. Ejemplos:

  • Subir una foto a la nube.
  • Sincronizar mensajes.
  • Reproducir música.
  • Obtener la ubicación periódicamente.

Los sistemas operativos limitan estas tareas para ahorrar batería (Doze en Android, Background App Refresh en iOS).

3. Tratamiento de notificaciones

Flujo típico:

  1. La app solicita permiso al usuario para mostrar notificaciones.
  2. Se crea un canal de notificación (Android 8+) con importancia y sonido.
  3. Cuando hay un evento (mensaje nuevo, recordatorio…), se construye la notificación y se muestra.
  4. El usuario puede tocar la notificación → la app se abre en la pantalla correspondiente.

También existen notificaciones push enviadas desde un servidor (Firebase Cloud Messaging, Apple Push Notification service).

4. Proceso de implementación (resumen)

  • Proveedores de contenido (Content Providers): permiten compartir datos entre apps de forma segura (Android).
  • Tareas en segundo plano: WorkManager (Android), BackgroundTasks (iOS), servicios foreground cuando es necesario.
  • Notificaciones: NotificationManager + canales (Android), UNUserNotificationCenter (iOS).

5. Servicios de cómputo en la nube aplicables

  • Firebase (Google): autenticación, base de datos, almacenamiento, Cloud Messaging, Functions.
  • AWS Amplify / Cognito / S3 / Lambda.
  • Azure Mobile Apps / Notification Hubs.
  • Supabase, Appwrite (alternativas open source).
  • Google Cloud / Cloud Run para backends personalizados.

Librerías y Toolkits

Qué son y cuáles son las más útiles en desarrollo móvil

◆ LIBRARIES · TOOLKITS · FRAMEWORKS
Jetpack Flutter React Native SwiftUI Room Retrofit Lottie Hilt

1. ¿Qué es una librería y qué es un toolkit?

Librería (Library)

Conjunto de código reutilizable que resuelve un problema concreto. Tú la llamas desde tu código.

Ejemplo: una librería para cargar imágenes desde internet (Glide, Coil).

Toolkit

Conjunto más amplio de herramientas, componentes y a veces un framework completo orientado a un tipo de desarrollo.

Ejemplo: Jetpack (Android), UIKit / SwiftUI (iOS), Flutter SDK.

2. Librerías de funciones especializadas (ejemplos)

  • Red: Retrofit, OkHttp, Alamofire, Dio.
  • Imágenes: Glide, Coil, Picasso, SDWebImage, cached_network_image.
  • Base de datos: Room, Realm, ObjectBox, Hive.
  • Inyección de dependencias: Hilt, Dagger, Koin, GetIt.
  • UI / animaciones: Lottie, MotionLayout, Rive.
  • Serialización: Gson, Moshi, Kotlinx.serialization, Codable.

3. Diferenciar toolkits aplicables a programación móvil

Toolkit / Framework Característica principal
Android Jetpack Conjunto oficial de librerías Android (Architecture, UI, Behavior…)
SwiftUI / UIKit Herramientas oficiales de interfaz de iOS
Flutter UI multiplataforma con un solo código (Dart)
React Native UI multiplataforma usando JavaScript/TypeScript y React
Xamarin / .NET MAUI Multiplataforma con C#
Kotlin Multiplatform Comparte lógica de negocio entre Android, iOS y más

Fuentes y referencias

Depuración y Seguridad

Encontrar errores y proteger la aplicación y los datos del usuario

1. ¿Qué es la depuración y la seguridad?

Depuración (debugging) es el proceso de encontrar y corregir errores (bugs) en el código. Se usa el depurador del IDE, logs, puntos de interrupción (breakpoints) y herramientas de análisis.

Seguridad abarca todas las medidas para proteger la app, los datos del usuario y la comunicación con servidores: cifrado, autenticación, almacenamiento seguro, protección contra ingeniería inversa, etc.

2. Herramientas de depuración incluidas en el entorno de desarrollo móvil

Android Studio
  • Debugger integrado
  • Logcat (logs en tiempo real)
  • Layout Inspector
  • Profiler (CPU, memoria, red, batería)
  • Network Inspector
  • APK Analyzer
Xcode (iOS)
  • LLDB debugger
  • Console y os_log
  • View Hierarchy Debugger
  • Instruments (tiempo, memoria, energía)
  • Network Link Conditioner
Flutter / React Native
  • Flutter DevTools
  • React Native Debugger
  • Chrome DevTools (para JS)
  • Hot Reload / Fast Refresh

3. Buenas prácticas de seguridad (resumen)

  • Nunca guardes contraseñas o tokens en texto plano.
  • Usa HTTPS siempre (Certificate Pinning cuando sea posible).
  • Almacena datos sensibles en Keychain (iOS) o EncryptedSharedPreferences / Keystore (Android).
  • Valida y sanitiza cualquier dato que venga del usuario o de la red.
  • Mantén las librerías actualizadas.
  • Ofusca el código en las versiones de producción (ProGuard / R8, bitcode, etc.).
